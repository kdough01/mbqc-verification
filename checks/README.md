# checks: the tests a DAG node can run

Every test is one file, `checks/<type>/<name>.py`, and its name is that path: `scaling/bilinear_formula` is
`checks/scaling/bilinear_formula.py`. The folder is the test's **type**. The type decides which question the
test answers (*truth*: is the statement true? *faithfulness*: does it say what we mean?) and the highest status a
pass can grant. A scaling test, for example, can never report "proved", whatever its code says. Each folder's
README explains its type and lists its tests.

## How a node runs a test

A node names the test and gives its parameters:

```yaml
checks:
- test: scaling/bilinear_formula
  params: {method: trotter2, compiler: graphix, quantity: N, coef: [10, -6, 3, 0]}
- test: lean/proof
- test: mutation/scaling_coefficients
```

`name:` sets the evidence file's name. It defaults to the type, and a node that runs the same type twice must
name each run.

`dagtool run` validates the parameters against the test's schema and runs the test. It writes the result to
`dag/evidence/<node>/<name>.json`, pinned to everything the verdict depends on: the node's statement, its
parents, the files it names under `code:`, the parameters, and the test's own code, including every helper it
imports. Changing any of these makes that evidence stale, and CI re-runs it.

```bash
dagtool tests                                     # every test, with a one-line summary and how often it is used
dagtool test scaling/bilinear_formula --node hamsim.B.trotter2.N.unopt     # run one now; writes nothing
dagtool test scaling/bilinear_formula --params '{"method": "qsvt", "quantity": "N", "coef": [294, -144, 362, -30]}'
dagtool run --node hamsim.B.trotter2.N.unopt      # run a node's checks and write their evidence
dagtool run --kind scaling/no_cancel              # every use of one test (or --kind scaling for a whole type)
```

## What every test file contains

1. **A docstring** with fixed sections, so that anyone can read what the test does without reading its code:

   | Section | Says |
   |---|---|
   | first line | `<type>/<name> — <one-line summary>` |
   | What it checks | the claim the test tests |
   | How it works | the steps, specific enough to reproduce by hand |
   | Parameters | every parameter: meaning, values, default |
   | Passes when / Fails when | the conditions, and what a failure means for the claim |
   | Grants | the status a pass gives |
   | Example | a node's `checks:` entry, as YAML (it is validated) |
   | Cost, Limits, Notes, See also | optional |

2. **`PARAMS` and `REQUIRED`**: the parameters as a JSON-schema literal. Unknown parameters and missing required
   ones are refused before the test runs.

3. **`run(node, params, ctx)`**, which returns a `Result` (`checks/_framework.py`). It can also define
   `applies_to(node)`, which returns False when the test should be skipped for that node.

Files that start with `_` are helpers, not tests. `checks/<type>/_x.py` serves one type; `checks/_shared/` serves
several (Lean runs, the scaling grids, predicates, comparisons, held-out values).

## Adding a test

```bash
dagtool new-test scaling my_test        # copies checks/_template.py to checks/scaling/my_test.py
# write the docstring, PARAMS and run()
dagtool readmes                         # adds it to checks/scaling/README.md
pytest tests/test_check_files.py        # the file follows the shape above and its Example validates
dagtool test scaling/my_test --params '{...}'
```

Then name it from a node (`- test: scaling/my_test`) and run `dagtool run --node <id>`. A new **type** also needs
a row in `checks/_kinds.py` (its question and ceiling) and a README in its folder.
